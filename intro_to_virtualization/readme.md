Задача 2
1. Для высоконагруженной базы данных Mysql, критичной к отказу, лучше всего подойдет физический сервер, который даёт максимальную производительность. Использование виртуализации создает виртуальные диски на ВМ, которые являются файлами на физическом хосте. Для работы с данными на накопителях это добавляет накладные расходы. Отказоустойчивость легко достигается на любой платформе.
2. Различные web-приложения покажут высокую эффективность, если они будут работать в виртуализации уровня ОС, когда на одном хосте можно запустить много контейнеров, каждый из которых изолирован. Web-приложения чаще всего это одна или несколько служб, которые слушают сетевой порт и обрабатывают запросы. Поэтому контейнеры подходит больше всего.
3. Windows-системы для использования бухгалтерским отделом лучше развернуть на паравиртуализационной платформе (например Hyper-V), которая позволит для каждого сотрудника отдела иметь свой рабочий стол благодаря службе RDS с сеансовым распрделением на одном физическом сервере. Также для этой задачи подходит паравиртуализационная платформ, т.к. пользвоателям неободим полный набор функционала ОС.
4. Системы, выполняющие высокопроизводительные расчеты на GPU будут работать эффективнее на физических серверах, где аппаратная часть не будет разделена на части.

Задача 3
1. Для первого сценария может подойти коммерческая система управления виртуализацией, например vSphere, если будет требование в поддерживаемости и скорость реакции на возникающие инциденты. Если особых требований нет, то отлично подойдет система Proxmox VE, которая основана на KVM. В Proxmox VE есть DRS (Distributed Resource Scheduler) для распределения нагрузки на гипервизорах, PBS (Proxmox Backup Server) для резервного копирования ВМ, снимки ZFS для фиксации состояния дисков виртуальной машины.
2. Для сценария с 20–30 серверами, смешанная среда Linux/Windows, требование «наиболее производительное бесплатное open source-решение» я бы снова остановился на выборе Proxmox VE. Proxmox VE настроен из коробки лучше чем чистый KVM.
3. Для этого сценария подходит Microsoft Hyper-V Server. Для Windows будет идеальным вариантом, так как это одна экосистема. Но есть минус - отсутствие удобных утилит управления, только cmd и ps.
4. Для тестирования программного продукта на нескольких дистрибутивах Linux лучше выбрать KVM (полноценные виртуальные машины). В отличие от контейнерных решений (Docker), KVM позволяет запустить каждый дистрибутив с его собственным ядром и полной системной средой, если продукт зависит от версии ядра, поведения systemd или загрузчика. KVM обеспечивает максимальную изоляцию и совместимость с любыми дистрибутивами.

Задача 4
Проблемы и недостатки:
1. Сложность управления и высокие требования к квалификации сотрудников. Вместо одной консоли администраторы вынуждены работать с несколькими. Это замедляет решение проблем и увеличивает вероятность ошибок из-за человеческого фактора.
2. Увеличение поверхности атаки. У каждого гипервизора свои уязвимости. Больше затрат на ИБ.
3. Проблемы совместимости при миграции и работе с оборудованием. Перенос виртуальной машины между хостами может привести к сбою загрузки.
4. Сложность резервного копирования. Единая политика бэкапа не работает: для каждой платформы нужны свои инструменты, свои процедуры восстановления и свои проверки. Это увеличивает время восстановления и риск того, что какая-то система останется без защиты.
5. Риск неоптимального использования ресурсов. Без единой системы управления ресурсы могут распределяться неравномерно: где-то простой, где-то перегрузка. Перемещение нагрузок между платформами вручную отнимает время.

Меры минимизации рисков:
1. Внедрить единый слой управления и мониторинга. Например, System Center Virtual Machine Manager (SCVMM), который позволяет управлять несколько систем. Для мониторинга — vRealize Operations, собирает метрики с разных платформ.
2. Стандартизировать образы ВМ и драйверы. Готовить эталонные образы с универсальными драйверами (VirtIO, синтетические драйверы Hyper-V/VMware), чтобы ВМ можно было переносить между платформами с минимальными правками.
3. Автоматизировать бэкапы через централизованные политики. Использовать инструменты, которые могут применять единые правила резервного копирования и обновления безопасности ко всем платформам, а не настраивать каждую отдельно.
4. Чётко разделить зоны ответственности. Определить, какие нагрузки на какой платформе живут и почему. Не допускать безконтрольного расползания ВМ по разным гипервизорам.
5. Обеспечить обучение персонала или нанять специалистов. Администраторы должны быть обучены по каждой из платформ, либо в команде должны быть люди, отвечающие за конкретные технологии.

Если бы у вас был выбор, создавали бы вы гетерогенную среду или нет?
Для новой инфраструктуры — нет. Однородная среда проще, дешевле в эксплуатации и снижает риски.
Если в организации уже есть несколько платформ, то одномоментная миграция всех нагрузок на одну платформу слишком рискованна или дорога. Оставил бы как есть.
